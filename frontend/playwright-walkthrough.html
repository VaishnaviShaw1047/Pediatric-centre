How Playwright was used to test the Pedia Centre frontend

Project: pedia-centre-frontend
Tool: Playwright 1.65 (Google Chrome)
Suite: 29 end-to-end tests in tests/e2e

1. What Playwright is doing

Playwright is a browser automation tool. It is not a unit tester. For this project it opens Chrome, loads the Angular app at http://localhost:4200, and behaves like a user: it clicks buttons, fills forms, follows routes, and checks that the screen shows the expected text and URLs.

The Angular app still thinks it is talking to FastAPI at http://127.0.0.1:8000/api/v1. Playwright intercepts every matching request inside the browser and returns fake JSON. That is why the suite can run without the Python backend, a database, or real users.

A typical test run does this:

  1. playwright.config.ts starts Angular with npm start and waits for port 4200 (unless the app is already running).
  2. Chrome launches. Each test gets a fresh page and empty storage.
  3. mockBackend(page) stubs all **/api/v1/** calls.
  4. The test navigates, clicks, and types as a parent, doctor, or admin.
  5. expect() checks URLs, headings, errors, and success messages.

These tests prove routing, role guards, form validation, and that each role area can complete its main jobs against mocked data. They do not prove real FastAPI rules, real JWT signing, or live database behaviour.

2. Installation

Playwright was added as a development dependency of this Angular repo:

npm install -D @playwright/test
npx playwright install chrome

The first command added "@playwright/test": "^1.65.0" to package.json. The second installs the Chrome channel that the config uses (channel: 'chrome'). If Chrome is not installed, either install Chrome or switch the config to Playwright’s Chromium and run npx playwright install chromium.

These scripts were added to package.json:

"test:e2e": "playwright test",
"test:e2e:ui": "playwright test --ui"

Angular’s own npm test was left as unit tests. End-to-end is a separate command. Generated output is ignored in .gitignore: test-results/, playwright-report/, blob-report/, playwright/.cache/, and playwright/.auth/.

3. Where the files sit

Test code lives at the repo root under tests/, next to src/, not inside Angular components. playwright.config.ts sets testDir to ./tests/e2e, so only *.spec.ts files there are executed. Helpers and page objects are imported; they are not run as tests.

A second doctor login exists only in the mock: DOC-TEMP / Temp@1234 returns must_change_password: true.

Fake JWT (tests/helpers/jwt.ts)

AuthService does not verify a server signature. It only needs a three-part token whose payload JSON has sub (user id) and exp (unix expiry). The helper base64url-encodes a header and payload and appends the dummy string test-signature.

How mockBackend works (tests/helpers/mocks.ts)

await page.route('**/api/v1/**', async (route) => { ... });

Angular HttpClient still posts to http://127.0.0.1:8000/api/v1/.... Playwright matches that URL pattern, reads method and path, and returns JSON with route.fulfill(). Anything unmapped returns 404 with “Unmocked METHOD path”, so a missing stub is obvious.

Examples of stubbed calls:

  • POST /auth/login — parent token or 401
  • POST /auth/doctor-login — schedule vs change-password
  • POST /registration — 201 plus MRN-101
  • GET /doctors/available — Meera Shah or an empty list
  • POST /appointments — APT-501
  • POST /doctors — staff id DOC099

Session is stored as localStorage.pc_session. AuthService reads that key. Tests either log in through the UI, or write the session with seedSession() so later pages can skip the login form. seedSession opens /login, then sets: 

localStorage.setItem('pc_session', JSON.stringify({
  token, role, userId, name, mustChangePassword
}))

6. Login page object

tests/pages/login.page.ts wraps the login screen so auth tests use names like “choose Parent” instead of repeating locators. Locators prefer roles and labels — the same names a person sees. 

await login.goto();
await login.login('Parent', '9876543210', 'Parent@123');
await expect(page).toHaveURL(/\/guardian\/find-doctor/);

Only login uses a page object. Other screens are clicked directly in the spec files with getByRole, getByLabel, and getByPlaceholder.

8. One test, step by step

Example: a parent books an appointment (guardian.spec.ts).

  1. beforeEach calls mockBackend(page), then seedSession(page, 'guardian').
  2. The test goes to /guardian/book/21. The role guard sees pc_session.role = guardian, so the page loads.
  3. Angular requests doctor 21 and the children list. Playwright returns Dr Meera Shah and Aarav / Anaya.
  4. The test selects child 101 and fills a date 7 days ahead. The app requests slots. The mock returns 10:00, 10:15, 11:00.
  5. The test clicks 10:00, types “Fever”, and clicks Confirm booking.
  6. POST /appointments is intercepted and returns 201 with APT-501. The UI shows “Appointment booked”.
  7. Click “View my appointments”. The URL becomes /guardian/my-appointments.

If the mock is wrong, the UI test fails. A 404 “Unmocked” path means the Angular service called an endpoint the fake API does not know. A missing heading means the component did not render the JSON that was returned.

9. What happens when you run the suite

  1. You run npm run test:e2e, which calls playwright test.
  2. Playwright reads playwright.config.ts.
  3. If port 4200 is down, it starts ng serve and waits.
  4. It collects tests/e2e/*.spec.ts.
  5. It runs them with one worker in Chrome and prints a list reporter.

Each test gets an isolated browser context: empty cookies and empty localStorage, unless the test writes them. After the last test, Playwright writes playwright-report/. Failures also land under test-results/ (screenshot, video, trace.zip).

10. Commands

Full suite:

npm run test:e2e
npx playwright test

Interactive UI mode (pick a spec, step through actions):

npm run test:e2e:ui

One file or one test title:

npx playwright test tests/e2e/auth.spec.ts
npx playwright test tests/e2e/guardian.spec.ts -g "books an appointment"

See the browser instead of headless:

npx playwright test --headed
npx playwright test --debug

Last HTML report, and a failure trace:

npx playwright show-report
npx playwright show-trace test-results/**/trace.zip

Locally you can keep ng serve running in another terminal. reuseExistingServer is true, so Playwright will not start a second Angular process. On CI, reuseExistingServer is false, retries are 2, and the job must have Chrome (or the config must drop channel: 'chrome').

12. How Playwright was introduced, in order

  1. Installed @playwright/test as a devDependency.
  2. Installed the Chrome channel Playwright drives.
  3. Added playwright.config.ts with baseURL port 4200 and webServer = npm start.
  4. Created tests/helpers: fixtures, jwt, session, then the route mock so every spec can call mockBackend(page).
  5. Created a small LoginPage for the three-role sign-in screen.
  6. Wrote specs in product order: smoke, auth, register, guards, guardian, doctor, admin.
  7. Wired npm run test:e2e and test:e2e:ui.
  8. Ignored report folders in .gitignore.

Mental model: Playwright is a remote control for Chrome. Angular is the app. mocks.ts is a pretend FastAPI sitting inside the browser. fixtures.ts is the clinic’s sample data. session.ts is a fake already-logged-in session. Spec files are the scripts that pretend to be Parent, Doctor, or Admin.

13. Cheat sheet

On a new machine:

npm install
npx playwright install chrome
npm run test:e2e

You do not need the backend. Only Node, npm packages, Chrome, and a working ng serve are required. When a test is red: read the terminal error, then the screenshot in test-results/, then the HTML report, then the trace viewer. If the error says Unmocked, extend mocks.ts.
